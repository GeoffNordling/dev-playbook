# RFC 2119 — Obligation Vocabulary

RFC 2119 defines a small set of uppercase modal verbs that authors use to
indicate the strength of each obligation in a normative document. This file
restates the standard as the standard defines it; it does not describe how
this workspace uses the standard. Our subset, formatting rules, and
per-item constraints are in [extensions.md](extensions.md).

Formal title: *Key words for use in RFCs to Indicate Requirement Levels*.
Author: S. Bradner, IETF, March 1997. Status: Best Current Practice (BCP 14).

RFC 2119 is clarified by RFC 8174 (May 2017), which states that only
**uppercase** occurrences of these words carry the defined meaning; the same
words in lowercase are ordinary English and carry no special force.

## Vocabulary

| Word | Synonyms | Meaning |
|---|---|---|
| `MUST` | `REQUIRED`, `SHALL` | Absolute requirement of the specification. |
| `MUST NOT` | `SHALL NOT` | Absolute prohibition of the specification. |
| `SHOULD` | `RECOMMENDED` | There may exist valid reasons in particular circumstances to ignore the item, but the full implications must be understood and carefully weighed before choosing a different course. |
| `SHOULD NOT` | `NOT RECOMMENDED` | There may exist valid reasons in particular circumstances when the behavior is acceptable or even useful, but the full implications must be understood and the case carefully weighed. |
| `MAY` | `OPTIONAL` | The item is truly optional. An author may include it to meet a particular need; another author may omit it, and interoperability with an implementation that omits it must still be possible. |

`MUST`, `SHALL`, and `REQUIRED` are exact synonyms. `MUST NOT` and `SHALL NOT`
are exact synonyms. RFC 2119 treats them as interchangeable; choosing between
them is an authorial preference, not a semantic distinction.

## Scope and framing

RFC 2119 is about obligation strength, not sentence structure. It says nothing
about how a requirement is phrased — only how strongly it binds. Sentence
structure is a separate concern, addressed by EARS (see [ears.md](ears.md)).

The standard also reminds authors that imperative language has cost.
Requirements should be used only where actually required for interoperability
or to limit harmful behavior (e.g., data loss, security breach).
Over-use of `MUST` dilutes the signal.
