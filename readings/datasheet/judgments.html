Concepts

Claim the plain-English proposition a judge rules true or false
Evidence / reference the files a claim is judged on; reference is context only, not itself ruled on
Content key a SHA-256 over the claim, instrument, and file bytes — the cache identity; any change re-keys
Instrument the model + effort a judge runs under, folded into the key
Seen-set the local store of keys already judged-and-passed
Cache-gate the pytest assertion that fails until a judgment's current content is in the seen-set

Spawns none
Net none

Purpose

Turns plain-English claims about a repo's files into cache-gated, LLM-judged checks — a project can assert things ordinary tests can't ("the README documents every flag") and have a judge model rule on them. The deterministic half — keying, prompt rendering, the seen-set — runs offline in pytest; the expensive judge runs only on a cache miss, and a recorded pass is never re-judged until the claim or its files change.

Behavior verified: run exhibit: constructed

$ judgments-run plan
{"schema": {…}, "seen": [],
 "unseen": [{"id": "readme-documents-flags", "model": "claude-opus-4-8",
   "effort": "high", "prompt": "Run `judgments-run render readme-documents-flags` …"}]}
$ judgments-run record readme-documents-flags   # after the judge rules it true
$ judgments-run plan
{"schema": {…}, "seen": ["readme-documents-flags"], "unseen": []}

The declaration (a claim plus its evidence/reference files) is fabricated for the demo, so the exhibit is constructed; the plan→record→plan run is live. First plan flags the judgment unseen with a ready-to-dispatch prompt; once a pass is recorded, the same content reads back seen and the cache-gate goes green.

Both CLIs above, the importable library below. judgments-run takes exactly one subcommand; <id> repeats for record. judgments-lint takes no arguments. Exit judgments-run: 0 ok · 1 bad config / unknown id / unreadable file · 2 usage. judgments-lint: 0 clean · 1 errors.

Shape

inputinternaloutput

One input — a repo's judgment declarations — flows through the loader and prepare into the seen-set; the three judgments-run subcommands and the pytest gate read or write that store. The judge itself is external: prepare renders the prompt, but no node here calls an LLM.

Module roster

loader.py — root resolution, glob discovery, field validation. core.py — prepare: single-read keying and prompt rendering, plus the fixed PROMPT and SCHEMA folded into the key. instruments.py — the valid model and effort sets. runner.py — the plan/render/record CLI. pytest_support.py — the cache-gate helper. skipcache/seen.py — the SQLite seen-set, a keys-only membership store carrying no domain vocabulary.

Assessment opinion

  1. A pass certifies exact bytes, not the claim's spiritthe content key folds in every evidence byte, so any edit to a judged file re-keys and forces a re-judge — a stale pass can't mask changed content, but a cosmetic edit re-charges the judge (Content key).
  2. The gate is only as strong as the machine it runs onthe seen-set is local and only the interactive run-judgments skill fills it; on CI the gate is skipped, so nothing verifies judgments there (Seen-set, Cache-gate).
  3. A recorded verdict is trusted, never re-checkedrecording a key asserts a pass, but nothing in scope runs the LLM or validates its ruling — a wrongly-recorded pass is invisible (Cache-gate).
  4. The model roster is hand-maintaineda config is rejected if its model isn't in the frozen set, so a newly-shipped model fails validation until someone edits the list (Instrument).
  5. Evidence-vs-reference rides on prompt wording alonethe two key differently, but only the instructions' prose tells the judge not to rule on reference material (Evidence / reference).
